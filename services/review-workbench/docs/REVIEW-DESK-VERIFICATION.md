# 三栏审核与估计进度

2026-09-10，用户要求恢复三栏、解释审核中心缺席原因、增加进度及原件错误框。

## 已核实的原因

审核中心原先只请求 `/jobs?pending_only=true`，当前 41 页转换任务的 `pending_blocks=0`、`pending_pages=0`，所以审核中心为空、处理任务仍可见。页面未说明这个筛选差异，造成文档审核缺席的体验。根因由只读 API 回读确认；审核范围与页级待审筛选已加入回归测试。

当前审核中心默认列出全部已完成转换结果，按待处理优先排列，提供“待人工处理”筛选。0 待审不改写为人工通过，标为“机器未报告待审 · 可抽查”。兼容旧适配服务：前端也按完成状态与待审计数过滤。真实页面已只读核实该 41 页文档出现，无生产写入。

## 已实现

- 固定工作区三栏：左侧问题清单，中间正文 / 表格，右侧原件。各栏独立滚动，任务详情默认折叠，不挤占审核空间。
- 上 / 下一个问题、物理页导航、待审过滤、正文块高亮、原件 50%–250% 缩放；1600px 与 1280px 桌面宽度检查通过。
- 复用现有 MarkdownEditor，可视化修改正文与 HTML 表格行列，也可编辑 Markdown 源码。特殊或不齐 HTML 仍使用源码模式，避免编辑器静默补格。
- 草稿只存当前浏览器 localStorage，键绑定 job / attempt / markdown SHA / block。修改后明确显示“已保存到本机 · 未提交生产修订”，清理浏览器数据会丢失草稿；没有生产文件写入、审核放行或自动制卡。
- 转换适配层只用既有 PDFium 后端读取页数元数据，不加载 OCR/LLM。新任务以已落盘识别记录、首轮复核回执估算 70% + 20% 工作量，收尾保留 10%；completed 才显示 100%。未知页数时为不定进度，不靠时钟虚增。这里不是耗时比例、预计剩余时间或内容通过率。

## 未实现伪精确框

只读检查当前 `docling-document.json` 的前三个文本来源记录，bbox 都是 `(0,0,0,0)`，charspan 也是 `[0,0]`。这是占位而不是原页位置，不能据此绘制精确错误矩形。页面明确提示缺少可靠坐标，仍采用页级联动及正文块高亮。本轮未引入新定位模型、未修改已冻结的转换模块，也未用 GPT/Codex 替代生产定位。
